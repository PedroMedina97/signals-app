2-3. Validación Básica y Estados de Campo (FieldState)

Demostración de validadores integrados, mensajes de error personalizados y estados de campo

Implementación: Cada FormControl mantiene un FieldState que incluye: value (valor actual), valid/invalid (estado de validación), touched/untouched (si el usuario interactuó), dirty/pristine (si cambió el valor), errors (objeto con errores), y status ('VALID', 'INVALID', 'PENDING', 'DISABLED'). La propiedad errors es clave: contiene un objeto donde cada validador fallido agrega una propiedad. Por ejemplo, minLength agrega un objeto con requiredLength y actualLength. Usamos estos datos para mostrar mensajes específicos. El FieldTree es la estructura jerárquica de todos los controles del formulario, permitiendo validación en cascada y acceso a cualquier campo mediante formGroup.get('fieldName').

4-5. Validadores Personalizados y Visualización de Errores

Creación de validadores personalizados para reglas de negocio específicas

Implementación: Los validadores personalizados son funciones que retornan ValidatorFn. Reciben un AbstractControl y devuelven ValidationErrors o null. Si retornan null, el campo es válido. Si retornan un objeto, cada propiedad representa un error. En este ejemplo, passwordStrengthValidator verifica múltiples condiciones (mayúsculas, minúsculas, números, caracteres especiales) y retorna un objeto detallado con el estado de cada condición. Esto permite mostrar exactamente qué falta para que la contraseña sea válida. El phoneValidator usa expresiones regulares para validar formatos específicos. Los validadores personalizados son reutilizables y pueden combinarse con validadores integrados usando arrays.

6-7. Validación Cruzada entre Campos y Condicional

Validadores que comparan múltiples campos y aplicación de reglas condicionales

Implementación: La validación cruzada (Cross-Field Validation) se aplica a nivel de FormGroup, no de campos individuales. Se configura en el tercer parámetro del constructor de FormGroup mediante la opción validators. El validador recibe el grupo completo y puede acceder a cualquier campo con group.get('fieldName'). passwordMatchValidator compara dos campos y retorna error si no coinciden. La validación condicional (Conditional Validation) evalúa reglas que dependen de otros valores: agePhoneValidator requiere teléfono solo si la edad es mayor o igual a 65. Estos errores se almacenan en formGroup.errors, no en campos individuales, por lo que deben mostrarse a nivel de formulario. Es un patrón poderoso para reglas de negocio complejas que involucran múltiples campos relacionados.

Validaciones Activas:

  • ✓ Las contraseñas deben coincidir (Cross-Field)
  • ✓ Teléfono requerido si edad >= 65 años (Condicional)
  • ✓ Email se puede deshabilitar dinámicamente

8-9. Formularios Anidados (Nested Forms)

Estructuras de formularios complejas con FormGroups anidados

Implementación: Los formularios anidados permiten organizar campos relacionados en grupos lógicos. Un FormGroup puede contener otros FormGroup como valores, creando una jerarquía o árbol (FieldTree). En este ejemplo, el formulario de dirección es un grupo independiente que se puede integrar en formularios más grandes. Los formularios anidados se validan en cascada: el padre es inválido si algún hijo es inválido. Para acceder a campos anidados se usa notación de punto: formGroup.get('address.street') o arrays: formGroup.get(['address', 'street']). Los valores se estructuran jerárquicamente. Este patrón es esencial para formularios grandes, permitiendo modularidad, reutilización y mejor organización del código.

10-11. FormArray - Trabajando con Listas Dinámicas

Gestión de listas de elementos con capacidad para agregar y eliminar items dinámicamente

Implementación: FormArray es un contenedor para un número variable de controles del mismo tipo. A diferencia de FormGroup (acceso por nombre), FormArray usa índices numéricos. Cada elemento puede ser un FormControl, FormGroup o incluso otro FormArray (arrays anidados). Métodos clave: push(control) agrega al final, removeAt(index) elimina por posición, insert(index, control) inserta en posición específica, at(index) accede a un elemento, clear() vacía el array, y length retorna el total. En el template usamos la directiva for para iterar. Cada control se enlaza con formControl. Los FormArrays se validan en grupo: si un item es inválido, todo el array es inválido. Es perfecto para formularios con listas de skills, teléfonos, direcciones, etc.

12. Formulario Completo con Validación Multi-Campo

Integración de todos los conceptos: formularios anidados, arrays, validaciones múltiples y envío al servidor

Implementación: Este ejemplo integra todos los conceptos anteriores en un formulario completo de producción. Combina FormGroups anidados (personalInfo, address), FormArray (skills), validaciones síncronas y asíncronas, estado de envío (isSubmitting), manejo de errores del servidor, y feedback visual completo. El proceso de envío incluye: 1) Validación local, 2) Estado "submitting" con UI bloqueada, 3) Llamada simulada al servidor, 4) Manejo de respuesta exitosa o errores, 5) Aplicación de errores del servidor a campos específicos usando control.setErrors(), 6) Feedback visual con mensajes y estados. Los errores del servidor se mapean a campos usando notación de punto (ej: 'personalInfo.email'). Este patrón es el estándar en aplicaciones reales donde la validación del servidor puede detectar conflictos que el cliente no puede conocer (emails duplicados, usuarios existentes, etc.).
