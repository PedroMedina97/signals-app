APIs de Resource en Angular - Gestión de Estado Moderna

1. Resource Básico con Fetch API

Demuestra la función resource() con fetch, manejo automático de AbortSignal, signals de estado/carga y capacidad de recarga

Implementación: Este ejemplo muestra cómo utilizar la función resource() para realizar peticiones HTTP usando la API nativa Fetch. El resource se define con un loader que es una función asíncrona que recibe un objeto params con un abortSignal. Este signal permite cancelar automáticamente las peticiones cuando el resource se recarga o el componente se destruye, evitando fugas de memoria. El resource expone tres signals fundamentales: value() para acceder a los datos, status() que indica el estado actual ('idle', 'loading', 'success', 'error'), y isLoading() que retorna un booleano. Al cambiar el userId signal, el resource detecta automáticamente el cambio y realiza una nueva petición, mostrando este comportamiento reactivo fundamental de las Resource APIs.

Estado: {{ userResource.status() }} Cargando: {{ userResource.isLoading() }}
@if (userResource.isLoading()) {
Cargando datos del usuario...
} @if (userResource.error()) {
Error: {{ userResource.error()?.message }}
} @if (userResource.value(); as user) {

{{ user.name }}

Email: {{ user.email }}

Phone: {{ user.phone }}

}

2. Resources con Parámetros y Manejo de Errores

Muestra cómo pasar parámetros a resources, manejar errores de forma elegante, y usar métodos reload() y set() para actualizaciones de valor local

Implementación: En este ejemplo avanzado, el resource lee reactivamente el signal searchQuery() dentro del loader. Cada vez que el usuario escribe en el input y el valor del signal cambia, el resource se recarga automáticamente. Se implementa validación con manejo de errores lanzando una excepción cuando la búsqueda tiene menos de 3 caracteres, lo cual se captura y muestra mediante error(). El método reload() permite refrescar manualmente los datos sin cambiar parámetros, útil para actualizaciones bajo demanda. El método set() es especialmente poderoso: permite establecer un valor local directamente sin ejecutar el loader, perfecto para implementar patrones de actualización optimista (optimistic updates) donde se muestra un resultado inmediato mientras se procesa en background. Los libros son clickeables y el selectedBookId se sincroniza para el siguiente ejemplo.

{{ booksResource.status() }}
@if (booksResource.isLoading()) {
Buscando libros...
} @if (booksResource.error()) {
{{ booksResource.error()?.message }}
} @if (booksResource.value(); as books) {
@for (book of books; track book.id) {

{{ book.title }}

por {{ book.author }}

${{ book.price }}

}
}

3. Usando linkedSignal para Estado Derivado

linkedSignal crea un signal escribible que se inicializa desde otro signal. Aquí, selectedBookId deriva del primer libro pero puede cambiarse manualmente

Implementación: linkedSignal() es una nueva API que resuelve un patrón común: crear un signal escribible que se inicializa computándose desde otros signals. A diferencia de computed() que es de solo lectura, linkedSignal() permite tanto lectura como escritura. En este caso, selectedBookId se inicializa automáticamente con el ID del primer libro de la búsqueda, pero cuando el usuario clickea otro libro en el ejemplo anterior, el valor se actualiza manualmente con set(). Este signal enlazado luego alimenta a bookDetailResource que carga los detalles del libro seleccionado. Cuando cambia booksResource (nueva búsqueda), el linkedSignal se reinicializa automáticamente al primer libro de los nuevos resultados, manteniendo la sincronización. Este patrón es esencial para estados UI que necesitan valores por defecto computados pero que pueden ser sobreescritos por interacción del usuario.

@if (bookDetailResource.isLoading()) {
Cargando detalles del libro...
} @if (bookDetailResource.value(); as details) {

{{ details.title }}

{{ details.description }}

Calificación: {{ details.rating }} / 5

Reseñas:

@for (review of details.reviews; track $index) {

{{ review }}

}
}

4. Flujos Observable con toSignal()

toSignal() convierte observables de RxJS a signals, funcionando sin problemas con HttpClient de Angular. Gestiona automáticamente las suscripciones según el ciclo de vida del componente

Implementación: Este ejemplo muestra cómo integrar Observables de RxJS con las Resource APIs. Aunque Angular 19+ introduce recursos nativos, muchas APIs y bibliotecas existentes retornan Observables (especialmente HttpClient). La estrategia aquí es envolver el Observable en una Promesa dentro del resource loader. Cuando cambia categoryId, el resource se recarga automáticamente, llamando al servicio getBooksByCategory() que retorna un Observable. Este patrón es útil durante migraciones graduales de código basado en RxJS hacia la nueva arquitectura de signals. El resource maneja la suscripción y desuscripción automáticamente, evitando memory leaks. Para casos donde no se necesita la reactividad completa de resource(), también se puede usar directamente toSignal() que convierte cualquier Observable en un signal de solo lectura, como veremos en ejemplos posteriores.

@if (categoryBooksResource.isLoading()) {
Cargando libros de categoría...
} @if (categoryBooksResource.value(); as books) {
@for (book of books; track book.id) {
{{ book.title }} - ${{ book.price }}
}
}

5. Tienda de Libros - Servicio de Estado con Resources

Gestión de estado centralizada usando un servicio con APIs de resource. Soporta signal de estado de palabra clave actual y datos compartidos entre componentes

Implementación: Este ejemplo demuestra el patrón de "State Service" moderno usando Resource APIs. El servicio BookStoreService actúa como una capa de gestión de estado centralizada donde se define un signal currentKeyword y un allBooksResource que reacciona a cambios en ese signal. Múltiples componentes pueden inyectar este servicio y acceder al mismo estado compartido. La búsqueda implementa debouncing (300ms) usando RxJS para evitar peticiones excesivas mientras el usuario escribe. El componente expone el estado del servicio mediante getters, separando la lógica de negocio de la presentación. Este patrón es superior a los antiguos servicios con BehaviorSubjects porque los signals son más eficientes, tienen mejor integración con el change detection, y los resources manejan automáticamente loading states, errores y cancelación. Es ideal para aplicaciones escalables donde múltiples componentes necesitan compartir y sincronizar estado.

Estado: {{ allBooksStatus }} Palabra clave: "{{ currentKeyword }}"
@if (allBooks; as books) {
@for (book of books; track book.id) {
{{ book.title }} ${{ book.price }}
}
}

6. Streaming con resource() y WebSockets

Demuestra streaming basado en promesas con resource(), incluyendo limpieza adecuada mediante AbortSignal

Implementación: Este ejemplo simula una conexión WebSocket usando resource() con Promesas. Aunque es una simulación con setInterval, el patrón es idéntico al de WebSockets reales. El loader retorna una Promesa que se resuelve cuando se reciben 5 mensajes (1 por segundo). Lo crucial aquí es el manejo de params.abortSignal: se registra un listener que cancela el interval cuando el signal se dispara (por reload o destrucción del componente). Esto previene memory leaks y conexiones huérfanas. El wsMessageCount signal se usa para generar diferentes mensajes en cada stream, demostrando cómo los resources pueden usar múltiples signals como entrada. Al hacer click en "Iniciar Nuevo Stream", se incrementa el contador y se llama a reload(), cancelando el stream anterior e iniciando uno nuevo. Este patrón es fundamental para manejar conexiones persistentes (WebSockets, Server-Sent Events, long polling) de forma segura y reactiva.

@if (wsResource.isLoading()) {
Conectando al stream...
} @if (wsResource.value(); as messages) {
@for (msg of messages; track $index) {
{{ msg }}
}
}

7. Streaming en Tiempo Real con toSignal()

toSignal() para streaming basado en observables proporciona actualizaciones de datos en tiempo real como precios de acciones o notificaciones en vivo con limpieza automática

Implementación: Este ejemplo utiliza toSignal() para convertir directamente un Observable en un signal de solo lectura. El servicio getStockPriceStream() retorna un Observable que emite precios cada 1.5 segundos usando interval() de RxJS. Al usar toSignal() con initialValue: 0, se crea un signal que se actualiza automáticamente con cada emisión del Observable. La ventaja sobre resource() es la simplicidad cuando no se necesitan capacidades de reload o set. La suscripción se maneja automáticamente: se crea cuando el componente se inicializa y se cancela cuando se destruye, sin necesidad de código manual de limpieza. Este patrón es perfecto para datos de streaming continuo (cotizaciones bursátiles, métricas en tiempo real, notificaciones push) donde el flujo de datos es constante y unidireccional. El template se actualiza reactivamente usando stockPrice sin paréntesis (getter), mostrando el precio formateado con dos decimales. Es la forma más limpia de integrar el mundo reactivo de RxJS con el nuevo sistema de signals de Angular.

${{ stockPrice.toFixed(2) }}
